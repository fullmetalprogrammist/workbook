Ты в целом хорошо уловил базовые **синхронные варианты + кэширование/локальная копия**, но в микросервисной архитектуре список шире. Твои 3 пункта — это скорее подмножество нескольких больших паттернов.

Разложу по “семействам”, чтобы было понятно, что ещё существует.

------

## 1. Синхронный запрос (request/response)

Твой вариант №1

**S1 → S2 по HTTP/gRPC каждый раз**

Это базовый вариант:

- всегда актуальные данные
- высокая связность по времени (S2 должен быть жив)
- возможна деградация всей цепочки

👉 Это часть более общего паттерна **Service-to-Service API call**

------

## 2. Локальная копия данных (data duplication / replication)

Твой вариант №2 — самый важный, и он шире, чем просто “если нет — сходи в S2”.

Варианты реализации:

### 2.1 Pull-based (как у тебя)

- S1 сам ходит в S2 и обновляет свою БД

### 2.2 Push-based (часто лучше)

- S2 сам “пушит” изменения в S1 (events)
- S1 просто поддерживает актуальную копию

👉 Обычно делается через:

- Kafka / RabbitMQ
- Event-driven architecture

------

## 3. Кэширование (cache-aside / read-through)

Твой вариант №3

Но тут тоже несколько вариантов:

- **cache-aside** (S1 сам проверяет кэш)
- **read-through cache** (кэш сам ходит в S2)
- **write-through / write-back** (реже для микросервисов)

------

## 4. Асинхронная событийная модель (Event-driven)

Это то, чего нет в твоём списке, но это один из основных подходов.

### Суть:

- S2 не отвечает на запросы “дай данные”
- S2 публикует события:
  - `UserUpdated`
  - `OrderCreated`
- S1 подписан и обновляет своё состояние

👉 Это по сути улучшенная версия твоего варианта №2, но:

- нет постоянных запросов
- нет tight coupling по API

------

## 5. CQRS / materialized views

Это уже “архитектурное усиление” варианта №2/4

- есть **write model (S2)**
- есть **read model (S1)** — заранее подготовленные данные

S1 вообще может не ходить в S2, потому что:

- у него уже есть “проекция” данных

------

## 6. API Composition (агрегация на уровне сервиса)

Вместо того чтобы S1 сам дергал S2:

- есть “композиционный слой” (BFF / API Gateway / aggregator service)
- он ходит в S1 и S2 и собирает ответ

------

## 7. Batch / ETL / периодическая синхронизация

- раз в N минут/часов S1 забирает данные из S2
- или через data pipeline

Используется когда:

- не нужна realtime-актуальность
- важна дешевизна

------

## 8. Shared database (антипаттерн)

- S1 и S2 используют одну БД

👉 Формально это “ещё один вариант”, но:

- ломает независимость сервисов
- обычно считается плохой практикой в микросервисах

------

## 9. Streaming / CDC (Change Data Capture)

Промежуточный вариант между БД и событиями:

- Debezium / CDC читает изменения из DB2
- стримит их в S1 или Kafka

👉 Это способ реализовать “почти realtime replication”

------

# Итог

Твои 3 варианта покрывают:

- sync call (1)
- local replication (2)
- cache (3)

Но **полная карта взаимодействий шире**:

### Основные классы:

1. Sync API calls
2. Async events (pub/sub)
3. Data replication (push/pull)
4. Cache layers
5. Precomputed read models (CQRS)
6. Aggregation layer (BFF/API Gateway)
7. Batch/ETL pipelines
8. CDC streaming
