# sDocker Compose зачем нужен

- Зачем нужен
  - `Docker Compose` - инструмент, позволяет разом запустить несколько контейнеров
    - Это удобнее, чем поднимать их по очереди руками из командной строки.
- Может быть полезно в случаях когда для работы одного контейнера нужен другой или они просто логично работают вместе
  - Например, если приложению для работы одновременно нужен ngnix и mysql, то вместо того, чтобы поднимать их по-отдельности, можно с помощью docker compose запустить разом и в нужном порядке. Или кафка, которая работает вместе с зукипером.
  - Или например поднимаем контейнер postgres, и контейнер с pgAdmin (чтобы не устанавливать локально), соответственно удобно будет запустить их вместе
- Запущенные вместе через docker-compose контейнеры формируют логическую группу
  - Ими разом можно управлять через эту группу, например, разом остановить
- DC в линуксе нужно устанавливать отдельно, а в винде он ставится автоматически вместе с docker engine при установке gui клиента докера.
- Проверить установку и узнать версию можно командами:

```
docker-compose -v
docker compose version
```



# Базовый пример

## Файл docker-compose

- Настройка dc производится в файле `docker-compose.yaml` (или yml) - стандартное имя
  - Файл можно положить куда угодно. Но обычно кладут в папку с программой, для которой поднимается инфраструктура.
- В DC указываются сервисы, конфиги, сети, секреты, тома.
  - Сервисы - это собственно говоря и есть приложения, которые должны работать вместе.

Простой пример docker-compose.yaml для запуска кафки и зукипера:

```yaml
services:
  zookeeper:
    image: confluentinc/cp-zookeeper:latest
    environment:
      ZOOKEEPER_CLIENT_PORT: 2181
      ZOOKEEPER_TICK_TIME: 2000
    ports:
      - 22181:2181
  
  kafka:
    image: confluentinc/cp-kafka:latest
    depends_on:
      - zookeeper
    ports:
      - 29092:29092
    environment:
      KAFKA_BROKER_ID: 1
      KAFKA_ZOOKEEPER_CONNECT: zookeeper:2181
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka:9092,PLAINTEXT_HOST://localhost:29092
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: PLAINTEXT:PLAINTEXT,PLAINTEXT_HOST:PLAINTEXT
      KAFKA_INTER_BROKER_LISTENER_NAME: PLAINTEXT
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
```

## Запуск

Открываем в консоли директорию, где лежит конфиг, и выполняем

```
docker compose up
```

## Остановка

- Запущенные контейнеры можно разом остановить из GUI.
- Можно сделать остановку из консоли
  - Если запускали через up, тогда можно просто нажать Ctrl + C в консоли
  - Или можно перейти в директорию с файлом docker-compose.yml, через который мы все запускали, и выполнить:

```
docker compose stop
```





# docker-compose и docker compose

- `docker-compose` - это старая версия утилиты
- `docker compose` - без дефиса, это новая версия
- Рекомендуется использовать новую
  - У нее лучше производительность, она развивается и поддерживает новые возможности.
- Если все же использовать docker-compose, то в yaml файлах надо добавлять параметр `version: '2'`

```yaml
version: '2'  # <--
services:
  # Описание сервисов
```

- Если docker compose, то version писать не надо, он все равно игнорирует этот параметр.

# Compose project

## Compose-проект

- Когда мы запускаем через docker compose всю канитель, описанную в compose-файле, то это называется `compose project`
- По умолчанию проект получает имя такое же как имя папки, в которой лежит compose-файл
- `-p` ключ позволяет задать произвольное имя проекту при старте (при остановке тоже нужен будет ключ -p)

```
docker-compose -p indamovie up
```

- Имя проекта можно задать в самом файле docker-compose.yaml, параметр `name`:

```yaml
name: in-da-movie
services:
  # остальная часть конфига
```

- Формат имени в kebab-case, через тире, например `my-awesome-project`, другие форматы не рекомендуется
- На что влияет имя проекта
  - Имя проекта добавляется по умолчанию к именам контейнеров, которые запускаются в рамках этого проекта

# Сервисы

## Пример описания сервиса

```yaml
services:
  nsp-postgres:  # <-- Имя сервиса
    image: postgres
    container_name: nsp-postgres  # <-- Имя контейнера
    environment:
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: admin123
      POSTGRES_DB: notifications_service
    volumes:
      - postgres_data:/var/lib/postgresql
    ports:
      - "5432:5432"
    command: >
      postgres -c shared_preload_libraries='pg_stat_statements'
              -c pg_stat_statements.track=all
              -c pg_stat_statements.max=10000
```

## Имя сервиса

- Имена сервисам надо давать через дефис, например `my-service`, другие форматы не рекомендуется
- Имя сервиса это абстракция, которая существует только в docker compose
  - Т.е. если мы просто запускаем контейнеры вручную, то у них никакого "имени сервиса" не бывает
- Главное назначение имени сервиса - это удобство service discovery внутри виртуальной сети, которую поднимает compose
  - Т.е. compose создал сеть, поместил в нее все сервисы, и внутри этой сети сервисы могут обращаться друг к другу по именам. Это по сути как DNS и ip-адреса.
    - Хорошо видно на примерах, например, кафки или других технологий, которым нужна например БД. Мы описываем в compose сервисы и в одних сервисах указываем имена других, т.о. связывая их.

## Имя контейнера

- Через container_name можно вручную указать докеру, под каким именем надо запустить контейнер.
  - Имена контейнерам надо давать через дефис, например `my-foobar-contaiter`, другие форматы не рекомендуется
- Обычно лучше не задавать имя контейнеру явно, потому что имена контейнеров дб уникальны в пределах всего движка докера.
  - Если например есть два разных compose файла, и в обоих будет два сервиса с одинаковым именем контейнера, и мы попробуем запустить разом эти compose файлы, то будет ошибка.
  - Если мы используем масштабирование (параметр scale или иной способ поднять несколько экземпляров сервиса), и при этом жестко задали имя контейнера, то докер попытается поднять все реплики под одинаковым именем и будет ошибка.
- По умолчанию докер дает имена контейнерам по формуле `compose проект + имя сервиса + N экземпляра`
  - Например, проект называется `notification-platform`, сервис называется `notification-service`, тогда имя контейнера будет `notification-platform-notification-service-1`
    - В докер gui имя может разбиваться для удобства чтения, но реальное имя контейнера можно посмотреть через docker ps, там будет видно что оно на самом деле такое длинное комплексное
- В общем, в compose-контексте имя контейнера не требуется вообще, все обращения можно делать через имя сервиса. Явное имя контейнера может потребоваться только в редких случаях, когда ты отчетливо понимаешь, зачем это делаешь. Во всех остальных случаях - не задавай.



# Запуск и остановка проекта

## Имя файла проекта

- Имя файла может быть произвольное, не обязательно `docker-compose.yaml`
- Но тогда при запуске и остановке надо через ключ `-f` указать имя файла

```
docker compose -f "my-docker-config.yaml" up
docker compose -f "my-docker-config.yaml" stop
```

- Можно указывать полный путь до файла, не обязательно переходить в директорию, просто так удобнее

## Два способа запуска - up и start

-  `docker compose up`
   - Это "полный" запуск, с проверками есть ли изменения в конфиге и применением этих изменений. Например, если появились новые сервисы, создадутся новые контейнеры. Если в уже созданных сервисах обнаружены изменения, то старые контейнеры удалятся и пересоздадутся с новыми настройками.
-  `docker compose start`
   - Это "быстрый" запуск, безо всяких проверок и запуском контейнеров как есть. Например, мы поработали, остановили контейнеры, никаких правок в конфиг не вносили. Тогда можно запустить просто через start. Если изменения в конфиге были, то они не применятся.

Итого:

- up - для самого *первого* запуска (т.к. надо создать контейнеры) и для запуска после внесения изменений в конфиг.
- start - только для *повторных* запусков, если изменений в конфиге не было.
  - Впрочем, up для повторных запусков тоже можно использовать, это не ошибка. Просто start может работать чуть быстрее в этом случае.

P.S. Я бы всегда через up запускал и не ебал мозги, потому что up еще в присоединенном режиме запускается, со всех сторон он выглядит выгоднее.

### Отсоединенный и присоединенный режим

- "Присоединенный" режим (attached) - это когда после запуска контейнеров docker compose "захватывает" консоль.
  - В консоль выводятся логи от контейнеров.
  - Через Ctrl + C можно остановить все контейнеры, т.к. докер ловит сигналы из консоли.
- "Отсоединенный" `detached` режим - это когда после запуска контейнеров docker compose "отпускает" консоль.
  - Логи от контейнеров не выводятся в консоль.
  - Сигналы, вроде Ctrl + C - не работают.
- По умолчанию up работает в присоединенном режиме, а start - в detached-режиме.
- Чтобы up запустился в detached-режиме, надо запускать с флагом `-d`

```
docker compose up -d
```

* start не может "присоединиться" ко всем контейнерам разом. Можно только настроить live-вывод логов:

```
docker compose logs -f
```

## Два способа остановки - down и stop

- `docker compose down`
  - Остановка с полным уничтожением всего - сети, контейнеров.
    - down вообще это удаление, но если контейнеры запущены то остановка + удаление.
- `docker compose stop`
  - Остановка без уничтожения - то же самое что нажать `Ctrl+C` (если запуск сделан не в detached-режиме)
- Не обязательно останавливать всю группу
  - У нас остается возможность перезапустить любой контейнер из группы независимо

# Тома (volumes)

- Имена томов принято писать через kebab-case, например `postgres-data`
  - Но при этом если выполнить docker volume ls, то можно увидеть, что докер полное имя формирует как `compose-project-name_volume-name`, т.е. разделяет подчеркиванием, а не дефисом.
- Имена томов должны быть уникальными в пределах docker engine. Соответственно, докер по умолчанию эту уникальность обеспечивает, добавляя имя compose-проекта к имени тома.
  - Но при необходимости можно явно задать имя, если надо как-то шарить том между разными проектами. Хз пока как, не приходилось, но возможность такая есть.



# Сеть

- По умолчанию docker compose создает сеть и все перечисленные в нем сервисы работают в этой сети
- На каждый compose-файл - отдельная сеть



# Продвинутая информация

## Как применить изменения в docker-compose.yaml

- Например, добавили сервис или изменили настройки для уже описанного сервиса
  - P.S. Думаю обычный docker compose up должен сделать как надо, но если вдруг нет, вероятно советы ниже пригодятся
- Надежнее всего сделать

```
docker compose down
docker compose up --force-recreate
```

- При stop - start изменения не применяются
- Если изменения только в одном или нескольких сервисах, можно выполнить `docker compose up --force-recreate foo1 bar2 etc3` чтобы пересоздавать только нужные контейнеры
  - foo1, bar2, etc3 - это имена сервисов, а не имена контейнеров



# Полезные тонкости

## Порядок запуска сервисов

- Через `depends_on` мы можем указать докеру, в какой последовательности он должен запускать сервисы. 
  - Однако докер не способен понять, нормально ли поднялся сервис с точки зрения бизнес-логики, например, произошло ли соединение с БД и все в этом роде. Он ориентируется на свои технические факты - запустилось, значит все нормально, запускаю следующий.
  - Поэтому нужно писать приложения таким образом, чтобы они в случае чего сами предпринимали попытки переподключиться к БД или опросить другой сервис на предмет корректной работы.
