# Способы выборки данных

Если говорить про **реальные коммерческие проекты на Spring Boot 3 + Spring Data JPA**, то список сильно сокращается.

### 1. Derived Query Methods (`findBy...`) — **используются везде** ⭐⭐⭐⭐⭐

Для простых запросов.

```java
findById(id)
findByEmail(email)
findByStatus(Status.ACTIVE)
findTop10ByOrderByCreatedAtDesc()
existsByEmail(email)
countByStatus(status)
```

Примерно **60–80%** запросов в типичном CRUD-проекте.

------

### 2. JPQL (`@Query`) — **очень часто** ⭐⭐⭐⭐⭐

Когда нужна:

- агрегация;
- join;
- fetch join;
- DTO;
- запрос слишком длинный для `findBy...`.

```java
@Query("""
select u
from User u
join fetch u.orders
where u.id = :id
""")
```

Практически стандарт де-факто.

------

### 3. Native SQL — **регулярно** ⭐⭐⭐⭐☆

Используют когда нужны возможности конкретной БД:

- `WITH`
- оконные функции
- `jsonb`
- `array`
- `unnest`
- `ON CONFLICT`
- `RETURNING`
- рекурсивные CTE

Особенно если PostgreSQL.

------

### 4. Specifications — **довольно часто** ⭐⭐⭐⭐☆

Самый распространенный способ делать динамические фильтры.

Например

```
GET /users?
    status=ACTIVE
    &ageFrom=18
    &ageTo=40
    &city=Berlin
```

Каждый параметр необязателен.

Именно здесь Specifications раскрываются лучше всего.

------

### 5. Проекции (DTO / Interface Projection) — **очень часто** ⭐⭐⭐⭐⭐

Во многих проектах вообще стараются **не возвращать Entity**.

```java
public interface UserDto {
    String getName();
    String getEmail();
}
```

или

```java
@Query("""
select new UserDto(
    u.id,
    u.name
)
from User u
""")
```

Это считается хорошей практикой.

------

### 6. Pageable / Sort — **почти всегда** ⭐⭐⭐⭐⭐

Практически любой список:

```java
Page<User> findByStatus(Status status, Pageable pageable);
```

или

```java
findAll(PageRequest.of(0, 20, Sort.by("createdAt")));
```

------

## Что встречается заметно реже

### QueryDSL

Есть проекты, где он основной инструмент (особенно старые корпоративные), но большинство новых проектов обходятся `Specifications` или пишут `@Query`. Если приходишь на новый проект, шанс увидеть QueryDSL есть, но далеко не гарантирован.

------

### EntityManager

Используется, но обычно скрыт внутри кастомных репозиториев, когда стандартного Spring Data недостаточно. Редко применяется для обычных CRUD-запросов.

------

## Что можно практически не изучать специально

- Criteria API (если знаешь Specifications — достаточно понимать, что они построены поверх него)
- NamedQuery
- Query by Example (`Example.of(...)`)
- Stored Procedures (если только проект не завязан на них)

Они существуют, но в большинстве современных Spring-проектов встречаются редко.

## Если бы нужно было подготовиться к собеседованию уровня Middle/Senior

Я бы рекомендовал уверенно владеть именно этим набором:

1. ✅ `JpaRepository` (`findById`, `findAll`, `save` и т.д.)
2. ✅ Derived Query Methods (`findBy...`)
3. ✅ `@Query` + JPQL
4. ✅ Native SQL
5. ✅ `Pageable` и `Sort`
6. ✅ DTO/Interface Projections
7. ✅ Specifications (динамические фильтры)

Эти семь инструментов покрывают подавляющее большинство запросов, которые действительно встречаются в современных Spring Data JPA-проектах.



# Кода какой выбирать

Это, пожалуй, самый правильный способ разделять их. Не по принципу "простые/сложные", а по **типу задачи**.

| Кейс                             | Derived Query (`findBy...`) | `@Query` + JPQL | Почему                                                       |
| -------------------------------- | --------------------------- | --------------- | ------------------------------------------------------------ |
| Поиск по одному полю             | ✅                           | ❌               | `findByEmail()`, `findByLogin()`. Название метода читается лучше, чем писать JPQL. |
| Поиск по нескольким полям        | ✅                           | ❌               | `findByFirstNameAndLastName()`, `findByStatusAndType()`. Пока название остается читаемым — derived выигрывает. |
| Диапазоны (`>`, `<`, `Between`)  | ✅                           | ❌               | `findByAgeGreaterThan()`, `findByPriceBetween()`. Есть готовые ключевые слова. |
| Сортировка                       | ✅                           | ❌               | `findTop10ByOrderByCreatedAtDesc()`. Намного компактнее.     |
| `exists`, `count`                | ✅                           | ❌               | `existsByEmail()`, `countByStatus()`. Для этого JPQL почти никогда не пишут. |
| Пагинация                        | ✅                           | ❌               | `findByStatus(Status s, Pageable p)`. Spring сам подставит limit/offset. |
| Простые связи (`findByAuthorId`) | ✅                           | ❌               | Spring умеет проходить по связям (`author.id`).              |

------

# Когда лучше JPQL

| Кейс                                     | Derived Query | JPQL | Почему                                                       |
| ---------------------------------------- | ------------- | ---- | ------------------------------------------------------------ |
| JOIN нескольких сущностей                | ⚠️             | ✅    | В derived нельзя явно управлять join'ами.                    |
| FETCH JOIN                               | ❌             | ✅    | `join fetch` невозможно выразить именем метода.              |
| DTO (`select new ...`)                   | ❌             | ✅    | Derived не умеет создавать DTO через конструктор.            |
| Агрегация (`count`, `avg`, `sum`, `max`) | ⚠️             | ✅    | Если нужен не просто `countBy...`, а группировка или вычисления. |
| GROUP BY                                 | ❌             | ✅    | Не поддерживается derived.                                   |
| HAVING                                   | ❌             | ✅    | Только JPQL.                                                 |
| Подзапросы                               | ❌             | ✅    | Derived такого не умеет.                                     |
| CASE WHEN                                | ❌             | ✅    | Только JPQL.                                                 |
| Сложные условия                          | ⚠️             | ✅    | Метод `findByStatusAndAgeGreaterThanAndCreatedAtBetweenAndCity...` быстро становится нечитаемым. |
| Кастомная сортировка                     | ❌             | ✅    | Например `order by case when ...`.                           |
| Выборка отдельных полей                  | ⚠️             | ✅    | Если нужны только `id` и `name`, JPQL позволяет не загружать всю сущность. |

------

# Хорошее практическое правило

## Используй Derived Query, если запрос можно описать одной понятной фразой.

```java
findByEmail()

findByStatus()

findByStatusAndType()

findTop10ByOrderByCreatedAtDesc()

existsByLogin()
```

Человек открывает репозиторий и сразу понимает, что делает метод.

------

## Переходи на JPQL, когда приходится "описывать SQL словами".

Например:

```java
findByStatusAndAgeGreaterThanAndCityAndRegistrationDateBetweenAndRoleOrderBySalaryDesc()
```

Такой метод уже сложно читать, поддерживать и изменять. Его лучше переписать как:

```java
@Query("""
select u
from User u
where u.status = :status
  and u.age > :age
  and u.city = :city
  and u.registrationDate between :from and :to
order by u.salary desc
""")
```

JPQL здесь гораздо нагляднее: структура запроса сразу видна, а при добавлении нового условия не приходится придумывать еще более длинное имя метода.

------

# Что чаще всего увидишь в реальном проекте

Обычно распределение выглядит так:

**Derived Query (~70%)**

- `findById`
- `findByEmail`
- `findByStatus`
- `existsBy...`
- `countBy...`
- `findTop10...`
- запросы с `Pageable`

**JPQL (~25%)**

- `join fetch`
- DTO-проекции
- агрегаты (`group by`, `count`, `sum`)
- отчеты
- запросы на 5–10 строк с несколькими условиями

**Native SQL (~5%)**

- специфичные возможности PostgreSQL/MySQL/Oracle (CTE, оконные функции, `jsonb`, `RETURNING`, и т.п.).

Такой подход соответствует тому, что обычно встречается в современных Spring Boot-приложениях: **не усложнять простые запросы JPQL, но и не пытаться выразить сложную логику через километровые имена методов**.
