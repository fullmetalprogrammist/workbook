

# .equals() и .hashCode()

## equals - это логическое "равно - не равно" для объектов

- `.equals()` это метод Object, используется для логического сравнения объектов на "равно - не равно"
  - Допустим, 5 == 5 это очевидно, а как сравнить два объекта Address, в которых много полей? Для этого у Address переопределяем equals и пишем в нем логику сравнения.
- В Object реализация equals сравнивает ссылки на объекты. А например Integer переопределяет метод и сравнивает значения, лежащие в обертках.
- Объекты на логическое "равно - не равно" всегда надо сравнивать через equals, иначе могут быть сюрпризы.
  - Например, Integer кэширует маленькие значения (в пределах byte) и два маленьких Integer по 100 могут оказаться равны по ==, а Integer по 200 уже будут не равны по ==, так что объекты - всегда сравнивать по equals надо.



## hashCode - это число от содержимого объекта

- `hashCode` физически это число int
- Если мы пишем сами реализацию хэша, то обычно пропускаем через хэш-функцию поля объекта
  - По умолчанию в Object реализация хэша зависит от JVM. Четких алгоритмов не известно, важно только что для одного и того же объекта метод .hashCode() должен возвращать одинаковый хэш
- Хэш нужен в основном для работы коллекций, основанных на хэш-таблице
  - Хэш по сути это быстрый способ понять, в какой бакет класть значение
- ✏️ Некоторые способы вычислить хэш

```java
Objects.hash(country, city, street, house, apartment);  // Типично когда надо единый хэш из нескольких полей
Long.hashCode(id);  // Integer.hashCode() и т.д.
somestring.hashCode();
```





## Взаимосвязь equals и hashCode

- Эти методы тесно связаны. hashCode отдельно обычно не переопределяют, обычно только в паре с equals.
- ⚠️ Правило - "переопределили equals - должны переопределить hashCode"
  - Почему? Потому что если equals для двух объектов дает true, то их хэши ⚠️ обязаны быть одинаковыми.
    - А почему вообще хэши объектов, которые равны по equals, обязаны быть одинаковыми? Что будет, если хэши будут разными?
      - Причина на самом деле проста. Возьмем например HashSet. В сете по определению не может быть двух одинаковых элементов, т.е. если a equals b, то a и b не могут в сете одновременно лежать. Представим, что хэши у них разные, тогда они окажутся в разных бакетах и тогда при добавлении b сет бы не нашел a. Соответственно, не понял бы что уже такой объект есть и добавил бы b. Вот поэтому хэши у них обязаны быть одинаковыми, чтобы сет по хэшу быстро нашел нужный бакет, а потом по equals бы уже проверил наверняка, есть такой объект или нет.

### Правило комбинаций полей

- ✅ Используем одинаковый набор полей в обоих методах. Идеальный вариант.

```
equals:    фамилия + имя + отчество;
hashCode:  фамилия + имя + отчество;
```

- ❌ В hashCode больше полей, чем в equals. Запрещено.

```
equals:    фамилия + имя;
hashCode:  фамилия + имя + отчество;
```

Почему? Потому что Петров Эдуард Иванович и Петров Эдуард Валентинович по equals равны (оба они Петров Эдуард), а хэши получаются разные (из-за отчества). Нарушается правило "объекты равны, значит дб одинаковый хэш"

- 🤔 В equals больше полей, чем в hashCode. Сомнительно, лучше так не делать.

```
equals:    фамилия + имя + отчество;
hashCode:  фамилия + имя;
```

Правило "объекты равны, значит дб одинаковый хэш" не нарушается, но получается больше коллизий, поэтому страдает производительность коллекций, основанных на хэш-таблицах. Например, Петров Эдуард Иванович, Петров Эдуард Валентинович, Петров Эдуард Семенович и все прочие Петровы Эдуарды попадут в один и тот же бакет. Стало быть будет больше линейного перебора при поиске объектов.



## Как писать equals и hashCode? Какие поля выбрать для сравнения?

- Базово сначала проверяется равенство ссылок, потом наследство и если это совпадает, тогда уже сравнение по полям.
- Выбираются поля, которые задают идентичность объекта:

```java
class Address {
    String country;
    String city;
    String street;
    int house;
    int apartment;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;  // <-- Базово проверяем на равенство ссылок
        if (!(o instanceof Address other)) return false;  // <-- и на наследство

        return house == other.house  // <-- Потом уже сравниваем поля
            && apartment == other.apartment
            && Objects.equals(country, other.country)
            && Objects.equals(city, other.city)
            && Objects.equals(street, other.street);
    }

    @Override
    public int hashCode() {  // <-- хэш считаем по полям, которые использовали в equals
        return Objects.hash(country, city, street, house, apartment);
    }
}
```

- Если у объекта есть какой-то идентификатор, id например, который и так однозначно его идентифицирует, то можно писать equals только по нему:

```java
class Person {
    long id;  // <-- Есть какой-то id'шник, поэтому можно только по нему сравнивать
    String name;
    int age;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Person person)) return false;
        return id == person.id;
    }

    @Override
    public int hashCode() {
        return Long.hashCode(id);
    }
}
```



## Дополнительные советы

- После помещения объекта в сет или в ключ мапы, основанные на хэш-таблицах, нельзя менять поля, которые участвуют в расчете хэша, т.к. хэш изменится и не удастся найти эти объекты.
- В lombok есть аннотации, упрощающие реализацию equals и hashCode. Просто влепить по всем полям наверное не стоит, но там есть более тонкие настройки. Стоит присмотреться, когда потребуется реализация.







# .compareTo()

- `.compareTo()` это метод интерфейса `Comparable`
- По умолчанию класс Object не реализует этот интерфейс. Однако реализация есть у подклассов, например String, Integer, LocalDate и т.д.
- Реализуя compareTo в классе, мы задаем `natural order` (естественный порядок) для экземпляров этого класса. Например, у чисел 1, 2, 3 порядок очевиден, а у объектов - нет. Поэтому чтобы было понятно как сравнивать объекты, мы должны реализовать compareTo.
- Сравнение используется в коллекциях на основе дерева, TreeSet, TreeMap например.
- compareTo желательно согласовать с equals. Если equals говорит, что объекты равны, то compareTo должен возвращать 0.
- compareTo обычно редко реализуют. В случаях, когда надо сравнивать элементы, у которых по своей природе нет естественного порядка, обычно используют объект типа `Comparator<T>`
